# Seed Data and Indexing

Builds on the `hotel_bookings` / `booking_events` schema with a larger,
varied seed dataset and an index tuned for one specific reporting query.

## Seed data

`init/02-seed-bookings.sql` was generated by `generate_seed.py` (included)
rather than hand-written, so the dataset is large and varied without
being tedious to maintain. Re-running the script reproduces byte-identical
output (fixed random seed + fixed reference "now").

What it contains:

| Requirement | What's actually in the data |
|---|---|
| ≥100 hotel bookings | **130** bookings |
| Multiple cities | **6**: delhi, mumbai, bengaluru, goa, jaipur, hyderabad |
| Multiple organizations | **4** distinct `org_id` values |
| Multiple statuses | All **4**: CONFIRMED, PENDING, CANCELLED, COMPLETED (weighted realistically — CONFIRMED/COMPLETED dominate) |
| Booking events for some bookings | **212** events across ~70% of bookings; the other ~30% intentionally have none, simulating bookings created before event tracking existed |

`created_at` values are spread over the last 90 days, skewed so a
meaningful chunk (77 of 130) falls inside the last 30 days — enough
that the target query's 30-day window has real rows to filter, not
just an edge case.

To regenerate with different volume/skew, edit the constants at the top
of `generate_seed.py` (`N_BOOKINGS`, `CITIES`, `ORGS`, `STATUS_WEIGHTS`)
and re-run it; it overwrites `init/02-seed-bookings.sql`.

## The query being optimized

```sql
SELECT org_id, status, COUNT(*), SUM(amount)
FROM hotel_bookings
WHERE city = 'delhi'
  AND created_at >= NOW() - INTERVAL 30 DAY   -- MySQL syntax (no quotes around 30 DAY)
GROUP BY org_id, status;
```

(The original spec's `INTERVAL '30 days'` is Postgres syntax; MySQL's
equivalent is `INTERVAL 30 DAY`, unquoted.)

## The index

```sql
CREATE INDEX idx_hotel_bookings_city_created_covering
  ON hotel_bookings (city, created_at, org_id, status, amount);
```

Applied in `init/03-indexes.sql`.

### Why this column order

- **`city` first**: it's the only equality (`=`) predicate in the
  `WHERE` clause. Equality columns belong first in a composite index so
  MySQL can jump straight to the matching block of rows.
- **`created_at` second**: it's a range predicate (`>=`). Per the
  left-prefix rule, a range column can only be used effectively as the
  index column immediately *after* the equality column(s) — columns
  placed after a range column in the index can no longer be used to
  narrow the scan, only to avoid a table lookup (see next point). So
  `(city, created_at)` is the natural stopping point for what actually
  drives the row selection.
- **`org_id, status, amount` appended, in that order**: these aren't
  used for filtering at all — they're in the index purely so the query
  never has to go back to the base table. This turns it into a
  **covering index**: once MySQL has narrowed rows down to
  `city = 'delhi' AND created_at >= ...` inside the index itself, it
  already has `org_id`, `status`, and `amount` sitting right there to
  aggregate, with zero extra row lookups against the clustered
  (primary key) data. `org_id`/`status` are included because they're
  the `GROUP BY` columns and `amount` because it's the value being
  summed — including it here means `SUM(amount)` doesn't need to touch
  the table either.

An index on `created_at` alone, or on `(city)` alone, would each only
solve half the filter. A plain `(city, created_at)` index (no trailing
columns) would still require a lookup back to the table for every
matched row to fetch `org_id`/`status`/`amount` — the covering version
avoids that entirely.

### What the index does *not* fix

The `GROUP BY org_id, status` still needs a temporary table/sort step
to aggregate — that's inherent to grouping and unrelated to how fast
the rows are found. What the index removes is the expensive part: a
full table scan to *find* the rows in the first place. On this dataset
that's the difference between scanning all 130 rows and scanning
exactly the 13 that match.

### Before / after, verified against the real seed data

**Before** (no index — `EXPLAIN` on the 130-row seeded table):

```
type: ALL           <- full table scan
key: NULL           <- no index used
rows: 130           <- scans every row
filtered: 3.33%      <- only ~4 rows actually matched, but all 130 were read
Extra: Using where; Using temporary
```

**After** (`idx_hotel_bookings_city_created_covering` in place):

```
type: range                                        <- index range scan, not a full scan
key: idx_hotel_bookings_city_created_covering
rows: 13                                            <- reads exactly the matching rows
filtered: 100.00%
Extra: Using where; Using index; Using temporary    <- "Using index" = covering, no table lookups
```

`EXPLAIN FORMAT=TREE` shows the same story more explicitly — before:
a `Table scan on hotel_bookings (cost=12.4 rows=130)`; after: a
`Covering index range scan on hotel_bookings using
idx_hotel_bookings_city_created_covering ... (cost=3.16 rows=13)`,
roughly a 4x estimated-cost reduction and a 10x reduction in rows
examined, on a table of only 130 rows — the gap widens as the table
grows, since the "before" plan always scans every row regardless of
table size while the "after" plan only ever touches matching rows.

Both plans were captured by actually running this seed data and this
query against a real local MySQL 8.0 instance (not estimated by hand),
and the query's result set (11 org/status groups for Delhi) was
confirmed identical with and without the index — the index changes
*how* the answer is found, not what the answer is.

## Applying this

If you're layering this onto the existing `local-db-test` project, drop
`02-seed-bookings.sql` and `03-indexes.sql` in place of the earlier
seed file (same `init/` folder, run order is `01` → `02` → `03`), then:

```bash
docker compose down -v   # fresh volume so init/ re-runs
docker compose up -d
```

Or, against an already-running container, apply just the new pieces:

```bash
docker compose exec -T mysql mysql -u root -p"$MYSQL_ROOT_PASSWORD" hotel_bookings_db < init/02-seed-bookings.sql
docker compose exec -T mysql mysql -u root -p"$MYSQL_ROOT_PASSWORD" hotel_bookings_db < init/03-indexes.sql
```
